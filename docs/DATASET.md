# Datasets

## Handling rules

- The raw Sentiment140 CSV is **not committed, not uploaded to the frontend, not served by any API endpoint**, and not
  copied. Scripts read it in place through `S140_PATH` (default
  `D:\Microsoft\sentiment analysis\archive\training.1600000.processed.noemoticon.csv`) as a single streaming pass.
- Samples derived from it (`data/interim/`, `data/processed/`) are gitignored.
- The deployed database `artifacts/analytics.db` contains the **synthetic** batch only (10,104 redacted reviews,
  IDs `R00001` to `R10192`). The only Sentiment140-derived content in it is aggregate: validation metrics and dataset
  statistics. A test checks that it holds no Sentiment140 text.
- One small fixture is committed for tests: `tests/fixtures/s140_fixture.csv`, 200 tweets with usernames pseudonymised by a SHA-256
  prefix. `artifacts/reports/pii_audit.json` keeps 23 *redacted* tweets as the record of the manual PII review.

## 1. Sentiment140 (real data, validation)

Source: Go, Bhayani & Huang (2009), 1.6M tweets labelled by emoticons (distant supervision).
Measured by `scripts/validate_dataset.py` (`artifacts/reports/dataset_validation.json`):

| Check | Value |
|---|---|
| Size / encoding | 238,803,811 bytes / latin-1 |
| Rows / columns | 1,600,000 / 6 (0 malformed rows) |
| Labels | 0 (negative): 800,000 · 4 (positive): 800,000 · **no neutral class** |
| Missing values | 0 |
| Duplicate tweet IDs | 1,685, all with conflicting labels. Every copy is excluded from the samples |
| Duplicate texts | 23,300 (case-insensitive exact) |
| Dates | 2009-04-06 → 2009-06-25 |
| Text length (chars) | min 3 · median 68 · mean 73.3 · p95 136 · max 373 |

Samples (seed 42): evaluation 5,000 (2,500 per label); batch 10,000 (5,000 per label, disjoint from evaluation).

**Used for:** sentiment accuracy (labelled validation), a real-text PII audit, and an end-to-end run on real text.
**Not suitable for:** themes, the Complaint Radar or drift. It is open-ended 2009 tweets with no product and only 11 weeks.
Running the full pipeline on it gives 95% theme noise, which is the honest result and is documented.

## 2. Synthetic "Nimbus" app reviews (planted ground truth)

`ml/data/synthetic.py`, generated by `scripts/generate_synthetic.py` (seed 42). The output is byte-identical across runs
(same SHA-256), and it is gitignored because it can be regenerated.

- **Size:** 10,192 rows over 84 days (2026-06-01 → 2026-08-23), with fields rating, platform, app version, created time and text.
- **Themes:** 13 planted themes plus invalid rows:
  - general praise 2,043
  - app crashes 1,629
  - UI praise 1,118
  - login problems 967
  - neutral / mixed 752
  - slow performance 705
  - delivery delays 694
  - battery drain 619
  - customer support 545
  - notifications 472
  - subscription pricing 461
  - payment failure 152
  - dark-mode request 27
  - invalid 8
- **Planted trends:**
  - payment failures start with app v5.3 (NEW);
  - battery drain ramps up (EMERGING);
  - crashes stay flat (STABLE);
  - login problems fade (DECLINING).
- **Planted PII:** 636 rows (about 6%) across 9 types: handles, account/order/customer IDs, phones, emails, card-like numbers, URLs and names. All values are
  fake: `example.com` addresses, 555 or +44 7700 phone numbers, test card numbers.
- **Dirty rows:** 3 null and 5 empty texts, about 0.8% ingestion duplicates, and 6 mojibake rows.
- **After cleaning:** 10,104 reviews are kept (80 duplicates and 8 empty rows removed).
- **Labels:** each row's template sentiment is kept as a weak label (negative 5,303 · positive 3,313 · neutral 1,576).
  It is *not* human annotation.

**Why synthetic:** no public dataset combines product reviews, timestamps, versions, known themes, known trends and known PII.
Planted ground truth makes theme recovery, radar statuses, drift and PII recall **measurable**.
**Limitation:** the reviews come from templates, so clustering is easier than on real data. Results on real reviews will be lower
than the synthetic scores in `docs/RESULTS.md`.

## Bring your own reviews

```powershell
.\.venv\Scripts\python.exe -m ml.pipeline --source path\to\reviews.csv --db artifacts\my_reviews.db
```

Column names are matched case-insensitively:

| Field | Required | Accepted column names |
|---|---|---|
| text | yes | text, review, review_text, content, body, comment, feedback |
| date | yes | created_at, date, timestamp, review_date, time, at, datetime |
| rating | no | rating, score, stars, star_rating |
| platform | no | platform, os, device |
| app version | no | app_version, version, review_created_version |
| ID | no | review_id, id, reviewid |

- **Dates:** ISO 8601 (with or without a timezone, converted to UTC) and common `d/m/Y` or `m/d/Y` forms are accepted. Ambiguous dates are read day-first.
- **Why dates are required:** the Complaint Radar and drift compare time windows. Dates are never invented: a file without a date column is rejected with an explanation. Rows with an unparseable date are still analysed for sentiment and themes, but are left out of the time windows.
- **IDs:** missing, unsafe or duplicate IDs are replaced by `U000001`-style IDs.
- **What gets stored:** the database records only the file name, never the local path.
- **Window coverage:** the radar needs at least 28 days of data (two 14-day windows).
- **Small batches:** small batches rarely reach the 30-mention threshold for NEW or EMERGING. This is intended, so that thin evidence does not raise alarms.

**Verified:** the synthetic batch saved with different column names (`Review, Date, Stars, Version`, no IDs, no platform) went
through the full pipeline in 44.0 s on the GPU. It produced the same 27 themes and radar statuses (Failing Payment NEW 0 → 140,
Battery EMERGING 111 → 243), and the traceability audit passed.
